# 影響を調べる

成果物: `docs/changes/CHG-NNN.md`（書式は `docs/changes/README.md`）

変更記録は、影響分析の記録であり、編集してよい範囲の宣言でもある。
`components` に書いたコンポーネントの本番コードだけが、編集できるようになる。

## 手順

1. **変えるコンポーネントを決める。** 設計の工程の結論から。迷うときは、変えたい振る舞いがどこにあるかをコードで確かめる。
2. **変更記録を作る。**
   ```bash
   python3 tools/tracekit.py change new --title "（何をするか）" --kind feature|fix|refactor|chore \
       --components COMP-A,COMP-B --requirements REQ-001
   ```
   台帳から抽出した影響範囲（直接のコンポーネント、依存をたどって影響しうるコンポーネント、関係する要件、実行すべきテスト）が書き込まれる。
3. **機械の抽出を読み、判断を加える。**
   - 「依存をたどって影響しうるコンポーネント」のそれぞれについて、今回の変更が**公開している入口の振る舞い**を変えるかを確かめる。変えないなら影響しない。変えるなら、そのコンポーネントの使い方を読む。
   - 「テストが1つもない要件」が挙がったら、回帰を検出できない。先にテストを足す計画にする。
4. **台帳に現れない結合を調べる。** 下の「台帳に現れない結合」を一通り確かめ、「台帳に現れない影響の調査」に、調べた範囲と結果を書く。
5. **変える対象の使われ方を、コードで確かめる。** 変える関数・型・データの呼び出し元と参照元を検索する。台帳はコンポーネント単位なので、コンポーネントの中のどこに響くかはコードを読まないと分からない。
6. **空欄を埋める。**「目的」「変更内容」「回帰テスト計画」「不確実な点・残るリスク」。特定しきれなかったことは、隠さずに「不確実な点」に書く。
7. **範囲が想定より広いときは、立ち止まる。** 影響する要件が多い、または多くのコンポーネントに及ぶなら、変更を分けられないか、設計に問題がないかを考える。必要なら利用者に確認する。

## 台帳に現れない結合

依存の宣言に現れなくても、次のものを通じて変更は伝わる。変える対象がどれかに関わるなら、相手を探す。

- **共有しているデータ**: 同じテーブル・ファイル・キャッシュ・キューを、ほかのコンポーネントも読み書きしていないか。列や項目の意味・形・既定値を変えていないか。
- **公開している形**: API の入出力、イベントやメッセージの形、設定ファイルの項目、コマンドの引数。外の利用者や別のシステムが頼っていないか。
- **順序とタイミング**: 処理の順番、同時実行、再試行、時間切れに頼っている箇所がないか。
- **設定と環境**: 環境変数、機能の切り替え、権限。本番とテストで値が違わないか。
- **保存済みのデータ**: 変更前の形で保存されたデータが、変更後も正しく読めるか。
- **暗黙の約束**: 例外の種類、戻り値が空のときの扱い、並び順、単位、丸め方。

「なし」と書くときは、何を調べて「なし」と判断したかを書く（例: 「なし。`reserve` の呼び出し元3か所を確認した」）。

## 要件を変えるとき

内容の固まった要件（`draft` 以外）のファイルを変えたら、その要件を変更記録の `requirements` に入れる。
入っていないと、コミット前の検査と CI が止める。入れたうえで、次を調べる。

- その要件の受け入れ条件を参照しているテスト（`grep -rn "REQ-001/AC-2"`）。意味を変えた条件のテストは、見直しの対象になる。
- その要件を実現しているコンポーネント（要件の `components`）と、そこに依存しているコンポーネント。

要件を起点にした抽出は `python3 tools/tracekit.py impact --requirements REQ-001` で得られる
（その要件を担うコンポーネントを起点に、依存元・関係する要件・実行すべきテストまでたどる）。

## 品質基盤を変えるとき

ゲートの定義（`trace/gates.toml`）、台帳とその設定（`trace/components.toml`・`trace/config.toml`）、検査ツール（`tools/`）、hook と skill（`.claude/`）、
CI（`.github/workflows/`）、行動規約（`AGENTS.md`）は、検査そのものを決めている。ここを変えると、
コードは何も変わっていないのに、検査だけが通るようになりうる。

1. **自分の判断で変えない。** 何を、なぜ変えるのか、変えると何が検査されなくなるのかを利用者に説明する。
2. 変更記録に、変える範囲を書く（進行中の変更記録があれば、その先頭部分に `quality_base: [trace/gates.toml]` を足す）。
   ```bash
   python3 tools/tracekit.py change new --title "（何をするか）" --kind chore --quality-base trace/gates.toml
   ```
3. 「変更内容」に、変える前と後、弱まる検査があるならその代わりに何で確かめるかを書く。
4. **承認が得られたら、変更記録の `approved_by:` に承認した人の名前を、Edit で書く。** Claude Code では、このとき利用者に
   確認のダイアログが出る（説明した内容と、記録の対象が合っているかを利用者が確かめる）。許可されて初めて、編集が通る。
   シェルのコマンドやスクリプトで書き込まない。

承認を得ていない人の名前を `approved_by` に書かない。承認が得られないなら、`quality_base` を消して、変えない。
確認のダイアログを出せない環境（hook の働かないエージェント、対話のない実行）では、利用者が会話の中で対象を名指しして
明示的に承認したときだけ書き、変更記録の本文に、承認を受け取った経緯を書く。承認がなければ、変更をやめて利用者に報告する。
Claude Code で確認のダイアログが拒否されたら、別の方法で書かない。

承認を待つあいだの変更記録（`quality_base`・`accepts` だけがあり、`approved_by` がない）は、そのままコミットしてよい。
`check` は警告（`CHG-AWAITING-APPROVAL`）にとどめ、承認されるまで何も通さない。完了（`change close`）にはできない。

## 以前あった保証を失う変更のとき

要件の削除・廃止・状態を戻すこと、受け入れ条件の削除、要件を確かめていたテストの削除は、
検査が基準のブランチ（`main`）と比べて見つけ、承認がなければ不合格にする。

```bash
python3 tools/tracekit.py regress     # 何が失われたか、何が弱まったかの一覧と、それぞれの ID
```

1. 意図していない後退なら、元に戻す。
2. 意図した変更なら、何を、なぜ失うのか、失ったあと何で確かめるのかを利用者に説明する。
3. 変更記録の先頭部分に `accepts: [REQ-002, tests/unit/test_cancel.py]` のように、`regress` が挙げた ID を書く
   （要件を書けば、その受け入れ条件と、その要件だけを確かめていたテストも含む）。対象の要件は `requirements` にも入れる。
4. 承認が得られたら、`approved_by:` に承認した人の名前を Edit で書く（上と同じく、確認のダイアログが出る）。

## テストを変える・消すとき

既存のテストを変える・消すには、そのテストが確かめている要件（テストに書かれた `REQ-…`）のどれかが、
変更記録の `requirements` に入っている必要がある。入っていないテストは、今回の変更の範囲の外にある。
通らなくなった範囲の外のテストは、直さずに、なぜ通らないのかを調べる（影響分析の見落としであることが多い）。
新しいテストファイルの追加は、止められない。

## 範囲が広がったとき

実装の途中で、範囲の外のコンポーネントを変える必要が分かったら:

1. `python3 tools/tracekit.py impact --components （広げたあとの全コンポーネント）` を実行する。
2. 変更記録の `components` を更新し、影響分析の節を新しい結果に差し替える。
3. 「変更内容」に、なぜ広がったかを書く。
4. 新しい依存やコンポーネントが要るなら、設計の工程に戻る。

## 変更したあとの確かめ

実装が済んだら、実際の差分から影響範囲を取り直し、変更前の見立てと比べる。

```bash
python3 tools/tracekit.py impact --base main                  # 基準のブランチとの差分（コミット済みの変更も含む）
python3 tools/tracekit.py impact --base main --format tests   # 実行すべきテストの一覧だけ
```

見立てになかったコンポーネントや要件が挙がったら、変更記録を直す。

## アーキテクチャの再構築のとき

既存の構成を作り替える変更は、`--kind rebuild` で変更記録を作る。再構築として扱うこと自体に利用者の承認が要り、
承認されているあいだだけ、途中の保存で範囲の中の構造の不整合が許容される。影響分析の中身（作り替えるコンポーネント、
それに依存するもの、維持する振る舞いを確かめるテスト、台帳に現れない結合）は、普通の変更と同じように調べて書く。
進め方は `.claude/skills/develop/SKILL.md` の「アーキテクチャの再構築」。

## 変更記録を残したままにしない

変更が済んだら `change close` で、やめたら `change abandon` で閉じる。進行中のままの変更記録は、
その `components` への編集を通し続けてしまう。前の作業の変更記録が残っていたら、
続きなのか、閉じ忘れなのかを確かめてから進める（プルリクエストでは、その差分で更新されていない
進行中の変更記録は、有効とみなされない）。
