# 実装する

始める前に、次がそろっていることを確かめる。そろっていなければ、前の工程に戻る。

- 対象の要件があり、受け入れ条件が書かれている
- 担当するコンポーネントが台帳にあり、置き場所（`paths`）が決まっている
- 進行中の変更記録があり、`components` に今回触るコンポーネントが入っている
- 受け入れ条件ごとの、テストケースの案がある

## 進め方

受け入れ条件を1つずつ、次の順で片づける。

1. **テストを書く。** 受け入れ条件を `REQ-001/AC-2` の形で書き添える。
2. **落ちることを確かめる。** 落ち方が「まだ実装がないから」であること。書き間違いや環境の問題で落ちているなら、テストを直す。
3. **通すための最小の実装を書く。** 置き場所は、台帳の `paths` の中。
4. **通ることを確かめる。** そのテストだけでなく、同じコンポーネントのテストも実行する。
5. **整える。** 重複、名前、責務の置き場所を見直す。振る舞いは変えない。テストが通ったままであること。

区切りごとに `python3 tools/tracekit.py check` を実行し、宣言していない依存や、どこにも属さないファイルができていないことを確かめる。

## 書くときの基準

- **その振る舞いを保証する責任があるコンポーネントに書く。** 呼び出す側に判定を漏らさない。相手のデータを取り出して、相手の代わりに判断しない。
- **ほかのコンポーネントは、公開している入口だけを使う。** 相手の内部のファイルや型に直接触れない。
- **依存は外から渡す。** 保存先・外部サービス・時計などを、関数やクラスの中で直接作らない。渡せる形にしておくと、テストで差し替えられる。
- **1つの関数・クラスは、1つの理由で変わる。** 判定と、保存と、通知が1か所に混ざったら、分ける。
- **抽象は、必要が現れてから足す。** 差し替える相手が1つしかないなら、インターフェースを先回りして作らない。
- **失敗を握りつぶさない。** 失敗したときに状態が途中で残らないこと。呼び出し側が、失敗を区別できること。

## hook に止められたとき

- **「進行中の変更記録がありません」** → そのコンポーネントは、変更記録の範囲に入っていない。影響分析に戻り（`analyze-impact` の「範囲が広がったとき」）、記録を更新してから続ける。hook を避けるために、シェルのコマンドでファイルを書き換えない。コミット前と CI の検査でも同じ規則が働く。
- **「どのコンポーネントにも属さない場所です」** → 置き場所が設計にない。既存のコンポーネントの責務に収まるなら、その `paths` の中に置く。収まらないなら、設計に戻る（`design-architecture`）。

## 設計と違う実装が必要になったとき

設計どおりに書けないと分かったら、黙って変えない。

1. 何が設計どおりにいかないのかを、具体的に書く（どの依存が足りないか、どの責務が収まらないか）。
2. 設計を直すのか、実装の方法を変えるのかを決める。骨格に関わるなら利用者に確認する。
3. 設計を直したら、台帳・設計書・変更記録を更新し、理由を残す。

## テストが通らないとき

1. 失敗の内容を読む。何を期待して、実際は何だったか。
2. 原因を突き止める。推測で直さない。値を出力する、範囲を狭める、最後に通っていた状態と比べる。
3. 実装を直す。受け入れ条件が変わっていない限り、テストの期待値は変えない。
4. 同じ原因が、ほかの箇所にもないかを確かめる。

3回直しても通らないなら、前提（設計、受け入れ条件の解釈、テストの立て方）を疑い、そこに戻る。

## 終える条件

- 対象の受け入れ条件すべてに、通るテストがある
- 要件の `verify` に書いたレベルすべてに、テストがある
- `python3 tools/tracekit.py check --no-matrix` にエラーがない
- 要件の `status` を `implemented` にした
