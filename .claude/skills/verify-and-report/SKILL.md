# 検証して完了にする

「できました」と言う前に、ここを通る。根拠は、いま実行した検査の結果だけ。前に通っていた、通るはず、は根拠にならない。

## 手順

1. **差分から、影響範囲を取り直す。**
   ```bash
   python3 tools/tracekit.py impact --base main
   ```
   基準のブランチ（既定は `main`）との差分から取る（`--base HEAD` だと、コミットした変更が入らない）。
   変更記録の見立てと比べる。見立てになかったコンポーネント・要件が挙がったら、変更記録を直す。
2. **基準のブランチと比べて、後退がないかを確かめる。**
   ```bash
   python3 tools/tracekit.py regress
   ```
   「承認されていない後退」があれば、意図していないものは元に戻す。意図したものは、利用者の承認を得て変更記録の `accepts` に書く
   （`.claude/skills/analyze-impact/SKILL.md` の「以前あった保証を失う変更のとき」）。
   「確かめてほしい点」に挙がったテスト（確かめる文が減った、大きく変わった）は、`test-reviewer` に必ず見せる。
3. **`test-reviewer` サブエージェントに、追加・変更したテストのレビューを頼む。** 指摘を直すか、直さない理由を変更記録に書く。
4. **コンポーネント・依存・公開している入口を変えた場合は、`design-reviewer` にも頼む**（設計の工程でレビュー済みで、そこから変えていなければ不要）。
5. **変更記録の空欄と、要件の状態を仕上げる。** 「レビュー」の節に、頼んだレビューの判定と、指摘への対応を書く（頼めなかったなら、その理由）。 対象の要件を `implemented` にする。実装中に分かったこと（設計と変えた点、広がった範囲、残るリスク）を変更記録に反映する。
6. **完了にする。**
   ```bash
   python3 tools/tracekit.py change close CHG-NNN
   ```
   マトリクスを作り直し、全ゲートを実行し、すべて通ったときだけ `done` になる。結果は変更記録に追記される。
   順番は「実装とテストをコミット → `change close` → 変更記録とマトリクスをコミット」にする
   （検証した時点のコミットが、変更記録に正しく残る）。
7. **通らなかったら、原因を調べて直し、もう一度実行する。** 下の「通らないとき」に従う。
8. **報告する。** 下の「報告に含めること」に従う。作業ブランチにコミットし、基準のブランチ（`main`）への取り込みは利用者に任せる。

サブエージェントを呼べない環境では、レビューを飛ばしたことにしない。「レビューを受けていない」と報告に書き、
利用者にレビューを頼む（設計の工程の `design-reviewer` も同じ）。

## 通らないとき

- **FAIL**: 出力を読み、原因を直す。ゲートのコマンドを書き換えて通す、対象を外して通す、ということをしない。
- **UNSET**（未設定のゲート）: そのゲートを、このプロジェクトでどう実行するかが決まっていない。コマンドを設定する（`adapters/README.md`）。実行しないと決めるのは利用者で、自分では決めない。`required = true` のゲートは外せない。利用者が承認したら、区分を `skip_kind` に（確かめる対象がないなら `not_applicable`、対象はあるが一時的に外すなら `waiver`）、理由を `skip_reason` に、承認した人の名前を `skip_approved_by` に書く。`waiver` には期限 `skip_until` が必須。
- **承認した人のない SKIP・期限を過ぎた SKIP の FAIL**: 自分で名前を埋めたり、期限を延ばしたりしない。利用者に、ゲートを設定するか、承認を取り直すかを確認する。
- **ゲートの設定（`trace/gates.toml`）を変える必要が出た**: 品質基盤の変更になる。利用者の承認を得て、変更記録の `quality_base` と `approved_by` に記録する（`.claude/skills/analyze-impact/SKILL.md` の「品質基盤を変えるとき」）。
- **`regress` の FAIL**: 基準のブランチと比べて、承認されていない後退がある。`python3 tools/tracekit.py regress` の一覧を見て、意図していないものは元に戻す。意図したものは、利用者の承認を得る。検査を通すために、要件の状態を戻したり、テストを消したりしていないかを、まず疑う。
- **テストのゲートが「0 件」「件数を読めない」で FAIL**: テストが実行されていない。コマンドの対象が合っているかを確かめる。`count_pattern` を外して通さない。
- **`trace` の FAIL**: `python3 tools/tracekit.py check` の指摘を1つずつ直す。台帳のほうを現状に合わせて直すのは、設計として正しいと説明できるときだけ。
- **`LEVEL-NOT-RUN`**: 要件が求めるレベルのテストを、どのゲートも実行していない。テストを書いただけでは検証にならない。ゲートに実行コマンドを設定する。要件の `verify` からそのレベルを外して通すのは、検証の水準を下げることなので、利用者に確認する。
- **直せない**: 完了にしない。変更記録は `active` のまま、何が通らないか・なぜ直せないか・どうすれば直せそうかを報告する。

## 報告に含めること

1. **何をしたか** — 1〜2文で。
2. **対応する要件** — 要件IDと、追加・変更した受け入れ条件。
3. **変更したコンポーネントとファイル**
4. **設計上の判断と理由** — 設計を変えたか、変えなかったか。変えたなら何をなぜ。
5. **追加・変更したテスト** — どの受け入れ条件を、どのレベルで確かめているか。
6. **品質ゲートの結果** — `change close` が出した一覧を、SKIP も含めてそのまま。SKIP のゲートは「検証していない」ものとして、理由・承認した人・期限を添える。
7. **影響分析の結果** — 影響しうると判断した範囲と、台帳に現れない結合について調べたこと。
8. **後退の検出の結果** — `tracekit.py regress` の「承認済みの後退」「確かめてほしい点」「承認として記録されているもの」を、そのまま。利用者は、これを読んで取り込むかを決める。
9. **残るリスクと未解決の点** — なければ「なし」。
10. **次に変更する人が注意すること** — あれば。

## 言ってはいけないこと

- 実行していないテストを「通った」と言う。
- SKIP や UNSET のゲートがあるのに「すべての検査に合格した」と言う。「7つのうち4つが合格、3つは承認つきで検証を外している（検証していない）」と言う。
- 確かめていない環境（本番、ほかのOS、実際の外部サービス）で動くと言う。
- 一部しか終わっていないのに「完了した」と言う。終わった部分と、終わっていない部分を分けて言う。
