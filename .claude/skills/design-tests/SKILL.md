# テストを設計する

成果物:
- 要件ファイルの `verify` と「検証の方針」
- 変更記録の「回帰テスト計画」
- 受け入れ条件ごとのテストケースの案（実装の工程で、最初に書くテストになる）

方針の全体は `docs/test-strategy.md` にある。ここでは、個々の要件についての決め方を扱う。

## 手順

1. **受け入れ条件を1つずつ取り上げ、「破られるとしたら、どこで破られるか」を考える。**
   - 規則そのものの誤り（計算、判定、境界） → 単体
   - コンポーネントのつなぎ目の誤り（渡し間違い、保存し忘れ、順序、失敗時の巻き戻し） → 結合
   - 相手との約束の食い違い（データの形・意味） → 契約
   - 入口から先の配線の誤り → E2E
2. **それを検出できる、最も下のレベルを選ぶ。** 下のレベルほど速く、落ちたときに原因を絞りやすい。
3. **リスクが高い条件は、上のレベルでも重ねる。** 壊れたときの損害が大きい、よく変わる、多くのコンポーネントにまたがる、のどれかに当てはまるとき。
4. **要件の `verify` に、必要なレベルを書く。** ここに書いたレベルにテストがないと、`implemented` にできない。「検証の方針」に、なぜそのレベルかを1〜2行で書く。
5. **テストケースの案を作る。** 受け入れ条件ごとに、入力・前提の状態・期待する結果を決める。期待する結果は、受け入れ条件から決める（これから書く実装からではない）。
6. **代用品を使う箇所と理由を決める。** 下の「代用品」に従う。
7. **回帰テスト計画を書く。** 変更記録の「実行すべきテスト」に、今回足す・直すテストを加える。
8. **`test-reviewer` サブエージェントに、テストケースの案のレビューを頼む**（リスクが高い要件、または受け入れ条件が4つ以上のとき）。

## テストケースの洗い出し

受け入れ条件1つにつき、テストは1つとは限らない。次を検討する。

- 境界: ちょうどの値、1つ下、1つ上、0、空、上限
- 同値の代表: 同じ扱いになる入力の集まりから、1つずつ
- 状態: 初期状態、処理済み、存在しない対象、順序が逆
- 失敗: 外部が失敗したとき。**失敗のあと、状態が変わっていないこと**
- 組み合わせ: 条件が互いに影響するときだけ。総当たりにしない

## 要件IDの書き方

テストには、確かめる受け入れ条件を `REQ-001/AC-2` の形で書く。テスト名・説明文・コメントのどこでもよい。
検査はテストファイルの中のこの文字列を探して、要件と対応づける。

```python
def test_rejects_order_beyond_stock():
    """REQ-001/AC-2 境界値: 在庫を1つ超える"""
```

```typescript
it("REQ-001/AC-2 在庫を超える注文は拒否され、在庫は変わらない", () => { ... });
```

```go
// REQ-001/AC-2
func TestRejectsOrderBeyondStock(t *testing.T) { ... }
```

1つのテストが、1つの受け入れ条件を確かめるのが基本。どの受け入れ条件にも当たらないテストが必要になったら、
要件の書き漏れか、内部の作りを確かめているかのどちらかなので、見直す。

## 代用品（モック・スタブ・フェイク）

- 置き換えてよいのは、コンポーネントの外側（保存先、外部サービス、時計、乱数）。
- 結合テストで確かめたいつなぎ目そのものは、置き換えない。置き換えると、テストは通るのに連携が壊れている状態を見逃す。
- 「何回呼ばれたか」を確かめるより、「結果として状態がどうなったか」を確かめる。
- 置き換えた理由を、テストファイルの先頭か該当箇所に書く。
- 外部の相手を置き換えたら、その相手との約束を契約テストで別に確かめる。

## テストが実装の誤りを写していないかの確かめ

- 期待値を、実装を動かして得た値から決めていないか。
- 実装と同じ計算式を、テストの中でもう一度書いていないか（同じ誤りが両方に入る）。
- そのテストは、実装が間違っていたら落ちるか。迷うなら、実装を一時的に壊して落ちることを確かめ、元に戻す。

## 不具合の修正のとき

1. 不具合を再現するテストを先に書き、**落ちることを確かめる**。
2. そのテストを、破られていた受け入れ条件に結びつける。
3. 既存のテストが、なぜこの不具合を検出できなかったかを1行で書く（レベルが合っていなかった、境界が抜けていた、代用品が隠していた、など）。同じ穴がほかの要件にもないかを考える。

## 既存のテストを変える・消すとき

- 受け入れ条件が変わった → テストを変えてよい。変更記録に、どの条件の変更によるものかを書く。
- 受け入れ条件は変わっていないのに、テストが落ちる → 実装が間違っている。テストを変えない。
- テストを消す → 対応する受け入れ条件がなくなったときだけ。
