# 検証して完了にする

「できました」と言う前に、ここを通る。根拠は、いま実行した検査の結果だけ。前に通っていた、通るはず、は根拠にならない。

## 手順

1. **差分から、影響範囲を取り直す。**
   ```bash
   python3 tools/tracekit.py impact --base main
   ```
   基準のブランチ（既定は `main`）との差分から取る（`--base HEAD` だと、コミットした変更が入らない）。
   変更記録の見立てと比べる。見立てになかったコンポーネント・要件が挙がったら、変更記録を直す。
2. **基準のブランチと比べて、後退がないかを確かめる。**
   ```bash
   python3 tools/tracekit.py regress
   ```
   「承認されていない後退」があれば、意図していないものは元に戻す。意図したものは、利用者の承認を得て変更記録の `accepts` に書く
   （`.claude/skills/analyze-impact/SKILL.md` の「以前あった保証を失う変更のとき」）。
3. **レビューの水準を確かめる。**
   ```bash
   python3 tools/tracekit.py change review CHG-NNN
   ```
   基準のブランチとの差分から、設計とテストのそれぞれについて「独立したレビューが必須」か「セルフレビューで足りる」かが、
   理由つきで出る。自分で「軽微だから」と判断して、必須と出たレビューを省かない。
4. **レビューを行う。** 下の「レビュー」に従う。必須と出たものは `design-reviewer`・`test-reviewer` に頼み、
   それ以外は自分で見直す。結果を、変更記録の「レビュー」の節と、先頭部分の `design_review`・`test_review` に書く。
5. **変更記録の空欄と、要件の状態を仕上げる。** 対象の要件を `implemented` にする。実装中に分かったこと（設計と変えた点、広がった範囲、残るリスク）を変更記録に反映する。
6. **完了にする。**
   ```bash
   python3 tools/tracekit.py change close CHG-NNN
   ```
   マトリクスを作り直し、レビューの状態を確かめ、全ゲートを実行し、すべて通ったときだけ `done` になる。
   結果（ゲートごとの結果と、レビューの水準・判定）は変更記録に追記される。
   順番は「実装とテストをコミット → `change close` → 変更記録とマトリクスをコミット」にする
   （検証した時点のコミットが、変更記録に正しく残る）。
7. **通らなかったら、原因を調べて直し、もう一度実行する。** 下の「通らないとき」に従う。
8. **報告する。** 下の「報告に含めること」に従う。作業ブランチにコミットし、基準のブランチ（`main`）への取り込みは利用者に任せる。

## レビュー

レビューの結果は、完了の条件になる。`change close` は、差し戻しと未実施を完了にしない。
途中のコミットは止めない（差し戻しのまま保存して、直してから完了にすればよい）。

| `design_review`・`test_review` に書く値 | 意味 | 完了にできるか |
|---|---|---|
| `pending` | 未実施（作ったときの値） | できない |
| `passed` | 独立したレビュー（実装した本人とは別の目）で合格した | できる |
| `rejected` | 独立したレビューで差し戻された（重大な指摘が残っている） | できない |
| `self` | 自分で見直した（セルフレビュー） | 独立したレビューが必須でなければ、できる |
| `not_applicable` | 見る対象がない（理由を「レビュー」の節に書く） | 独立したレビューが必須でなければ、できる |

**独立したレビューが必須と出たとき**

1. サブエージェントに頼む（設計は `design-reviewer`、テストは `test-reviewer`）。依頼には、変更記録の ID、対象の要件、
   `change review` が挙げた理由を書く。`regress` の「確かめてほしい点」に挙がったテストがあれば、それも伝える。
2. 判定を写す。合格なら `passed`、差し戻しなら `rejected`。「レビュー」の節に、誰が見たか、判定、指摘への対応を書く。
3. **差し戻しなら、重大な指摘（修正の必要性: 必須）を直し、同じレビュー担当にもう一度頼む。** 前回の指摘と、直した内容を伝える。
   合格するまで、完了にできない。
4. 指摘に同意できないときは、自分で `passed` と書かない。指摘と自分の見解を利用者に示して、判断を求める。
5. 改善の指摘（修正の必要性: 推奨・任意）は、直すか、直さない理由を「レビュー」の節に書く。合格の妨げにはならない。

受けていないレビューを `passed` と書かない。サブエージェントを呼べない環境では、利用者（実装した本人以外の人）に
レビューを頼み、結果が出るまで `pending` のままにする（完了にしない。そのことを報告に書く）。

**必須と出なくても、独立したレビューを頼むとき**（機械の判定は下限。差分に現れない重要な変更は、自分で気づいて頼む）

- 公開している入口（ほかのコンポーネントや外から使われる関数・型・データの形）を変えた
- 台帳に現れない結合（共有するデータ、イベント、設定値）を足した
- お金・在庫・権限・個人情報など、壊れたときの損害が大きい規則（業務上の不変条件）に手を入れた
- 自分の見直しで、判断に迷う点が残った

**セルフレビューで足りるとき**

次の問いに答え、結果（何を見直し、何を直したか）を「レビュー」の節に1〜3行で書く。問いのどれかに「はい」と答えられないなら、
直すか、独立したレビューを頼む。

- 設計（`design_review: self`）
  - 今回足した・変えたコードは、そのコンポーネントの責務（`responsibility`）に収まっているか
  - 新しい依存・共有するデータ・設定値を足していないか（足したなら設計の変更。設計の工程に戻る）
  - 公開している入口の形と振る舞いを変えていないか
- テスト（`test_review: self`）
  - 受け入れ条件の THEN に書かれた結果を、テストが実際に検査しているか
  - 実装が間違っていたら落ちるか（迷うなら、実装を一時的に壊して落ちることを確かめ、元に戻す）
  - 境界、異常な入力、失敗のあとに状態が変わらないことを押さえているか

見る対象がないなら `not_applicable` とし、理由を書く（例: 「設計: 対象外。文書とテストだけの変更」
「テスト: 対象外。振る舞いを変えない整理で、既存のテストが通ることを確かめた」）。

## 通らないとき

- **FAIL**: 出力を読み、原因を直す。ゲートのコマンドを書き換えて通す、対象を外して通す、ということをしない。
- **「レビューが差し戻しのままです」「独立したレビューの合格が必須です」「レビューが未実施です」**: 上の「レビュー」に従う。
  要る水準を下げるために、変更記録の範囲（`components`・`requirements`・`quality_base`）から対象を外さない
  （範囲の外の変更は、hook とコミット前の検査が止める）。「比べられないため、重要度を判定できません」と出たら、
  基準のブランチ（`trace/config.toml` の `base_branch`）があるかを `python3 tools/tracekit.py doctor` で確かめる。
- **コミットが「ステージした内容と、作業ディレクトリの内容が違います」で止まる**: 検査は作業ディレクトリを読むので、
  そのままでは確かめていない内容がコミットされる。コミットに入れるものを `git add` し直す。`--no-verify` で通さない。
- **再構築（`kind: rebuild`）を完了にできない**: 途中の保存で許容されていた不整合は、完了のときはすべてエラーになる。
  `python3 tools/tracekit.py check`（`--in-progress` なし）のエラーを解消する。解消しきれないなら、完了にせず、
  残っている不整合と見通しを報告する。完了にするために、ゲートや検査を緩めない。
- **UNSET**（未設定のゲート）: そのゲートを、このプロジェクトでどう実行するかが決まっていない。コマンドを設定する（`adapters/README.md`）。実行しないと決めるのは利用者で、自分では決めない。`required = true` のゲートは外せない。利用者が承認したら、区分を `skip_kind` に（確かめる対象がないなら `not_applicable`、対象はあるが一時的に外すなら `waiver`）、理由を `skip_reason` に、承認した人の名前を `skip_approved_by` に書く。`waiver` には期限 `skip_until` が必須。
- **承認した人のない SKIP・期限を過ぎた SKIP の FAIL**: 自分で名前を埋めたり、期限を延ばしたりしない。利用者に、ゲートを設定するか、承認を取り直すかを確認する。
- **ゲートの設定（`trace/gates.toml`）を変える必要が出た**: 品質基盤の変更になる。利用者の承認を得て、変更記録の `quality_base` と `approved_by` に記録する（`.claude/skills/analyze-impact/SKILL.md` の「品質基盤を変えるとき」）。
- **`regress` の FAIL**: 基準のブランチと比べて、承認されていない後退がある。`python3 tools/tracekit.py regress` の一覧を見て、意図していないものは元に戻す。意図したものは、利用者の承認を得る。検査を通すために、要件の状態を戻したり、テストを消したりしていないかを、まず疑う。
- **テストのゲートが「0 件」「件数を読めない」で FAIL**: テストが実行されていない。コマンドの対象が合っているかを確かめる。`count_pattern` を外して通さない。
- **`trace` の FAIL**: `python3 tools/tracekit.py check` の指摘を1つずつ直す。台帳のほうを現状に合わせて直すのは、設計として正しいと説明できるときだけ。
- **`LEVEL-NOT-RUN`**: 要件が求めるレベルのテストを、どのゲートも実行していない。テストを書いただけでは検証にならない。ゲートに実行コマンドを設定する。要件の `verify` からそのレベルを外して通すのは、検証の水準を下げることなので、利用者に確認する。
- **直せない**: 完了にしない。変更記録は `active` のまま、何が通らないか・なぜ直せないか・どうすれば直せそうかを報告する。

## 報告に含めること

1. **何をしたか** — 1〜2文で。
2. **対応する要件** — 要件IDと、追加・変更した受け入れ条件。
3. **変更したコンポーネントとファイル**
4. **設計上の判断と理由** — 設計を変えたか、変えなかったか。変えたなら何をなぜ。
5. **追加・変更したテスト** — どの受け入れ条件を、どのレベルで確かめているか。
6. **品質ゲートの結果** — `change close` が出した一覧を、そのまま。次の5つを混ぜない。
   | 表示 | 意味 |
   |---|---|
   | `PASS` | 実行して、合格した |
   | `FAIL` | 実行して、失敗した（または、ゲートの外し方が認められない） |
   | `SKIP:対象外` | 確かめる対象がない（承認つき）。理由と承認した人を添える |
   | `SKIP:免除` | 対象はあるが、検証していない（承認された例外）。理由・承認した人・期限を添える |
   | `UNSET`・`NOTRUN` | 未設定（未導入）・今回は実行していない（一部だけの実行、基準のブランチと比べられなかった） |
7. **レビューの結果** — 設計とテストのそれぞれについて、求められた水準（独立したレビューか、セルフレビューか）とその理由、
   誰が見たか、判定、直した指摘、直さずに残した改善の指摘と理由。
8. **影響分析の結果** — 影響しうると判断した範囲と、台帳に現れない結合について調べたこと。
9. **後退の検出の結果** — `tracekit.py regress` の「承認済みの後退」「確かめてほしい点」「承認として記録されているもの」を、そのまま。利用者は、これを読んで取り込むかを決める。
10. **残るリスクと未解決の点** — なければ「なし」。
11. **次に変更する人が注意すること** — あれば。

## 言ってはいけないこと

- 実行していないテストを「通った」と言う。
- SKIP・UNSET・NOTRUN のゲートがあるのに「すべての検査に合格した」と言う。「7つのうち4つが合格、2つは対象外、1つは免除（対象があるのに検証していない）」と言う。
- 受けていないレビューを「レビュー済み」と言う。セルフレビューを「レビューで合格した」と言う。差し戻しのまま「完了した」と言う。
- 確かめていない環境（本番、ほかのOS、実際の外部サービス）で動くと言う。
- 一部しか終わっていないのに「完了した」と言う。終わった部分と、終わっていない部分を分けて言う。
