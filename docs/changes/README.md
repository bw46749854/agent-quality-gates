# 変更記録

本番コードや品質基盤を変えるたびに、変更記録を1つ作ります。変更記録は**影響分析の記録**であり、
同時に**編集してよい範囲の宣言**でもあります。
手順は `.claude/skills/analyze-impact/SKILL.md` にあります。

## 流れ

```bash
# 1. 作る（台帳から抽出した影響範囲が、あらかじめ書き込まれる）
python3 tools/tracekit.py change new --title "二重キャンセルを拒否する" --kind fix \
    --components COMP-ORDER --requirements REQ-002

# 2. 空欄を埋める → 実装する

# 3. レビューの水準を確かめる（独立したレビューが必須か、セルフレビューで足りるか）→ レビューして、結果を書く
python3 tools/tracekit.py change review CHG-001

# 4. 完了にする（レビューが済み、全ゲートを通ったときだけ done になる。結果は記録に追記される）
python3 tools/tracekit.py change close CHG-001
```

途中でやめるときは `python3 tools/tracekit.py change abandon CHG-001 --reason "…"`。

## 先頭部分（フロントマター）

| 項目 | 意味 |
|---|---|
| `status` | `active`（進行中） / `done`（完了） / `abandoned`（中止） |
| `kind` | `feature`（要件の追加・変更） / `fix`（不具合の修正） / `refactor`（振る舞いを変えない整理） / `chore`（それ以外） |
| `requirements` | 対象の要件。`feature` と `fix` では必須。**内容の固まった要件（`draft` 以外）のファイルを変えたときは、その要件をここに入れる**（入っていないと、コミット前の検査と CI が止める） |
| `components` | **編集してよいコンポーネント。** ここにないコンポーネントの本番コードは、hook とコミット前の検査が止める |
| `quality_base` | **編集してよい品質基盤のパス**（glob 可。例: `[trace/gates.toml, tools/**]`）。品質基盤を変えないなら書かない |
| `accepts` | **受け入れる後退**（`tracekit.py regress` が挙げた ID。例: `[REQ-002, REQ-001/AC-3, tests/unit/test_x.py]`）。後退がないなら書かない |
| `approved_by` | `quality_base` と `accepts` を承認した人の名前。どちらかを書いたら必須。**承認を得てから、Edit で書く** |
| `design_review`・`test_review` | 設計とテストのレビューの結果。`pending` / `passed` / `rejected` / `self` / `not_applicable`（下の「レビュー」） |

## レビュー

機械の検査（品質ゲート）がすべて通っても、責務の分け方やテストの中身が妥当かは分かりません。そこを見るのがレビューで、
その結果は**完了の条件**です。設計（`design_review`）とテスト（`test_review`）のそれぞれに、状態を1つ書きます。

| 値 | 意味 | 完了にできるか |
|---|---|---|
| `pending` | 未実施（変更記録を作ったときの値。項目がない場合も同じ） | できない |
| `passed` | 独立したレビュー（`design-reviewer`・`test-reviewer`、または実装した本人以外の人）で合格した | できる |
| `rejected` | 独立したレビューで差し戻された（直すべき重大な指摘が残っている） | できない |
| `self` | 実装した本人が見直した（セルフレビュー） | 独立したレビューが必須でなければ、できる |
| `not_applicable` | 見る対象がない（理由を「レビュー」の節に書く） | 独立したレビューが必須でなければ、できる |

すべての変更に同じ重さのレビューを求めると、小さな修正のたびに手間がかかり、形だけになります。そこで、
**独立したレビューを必須にするのは、重要な変更だけ**です。重要かどうかは、エージェントの自己申告ではなく、
基準のブランチ（`main`）との差分から機械が判定します。

```bash
python3 tools/tracekit.py change review CHG-001
```

| 差分に現れた変更（その変更記録の範囲のもの） | 必須になるレビュー |
|---|---|
| コンポーネントの新設・削除、責務（`responsibility`）・依存先（`depends_on`）・境界（`paths`）・状態（`status`）の変更 | 設計（`design_review: passed`） |
| 重要な要件（`priority: must`）を新しく定めた・廃止した・受け入れ条件や検証レベル（`verify`）を変えた | テスト（`test_review: passed`） |
| その変更の要件を確かめていたテストが消えた・減った・大きく削られた（確かめる文が減った、半分以下になった） | テスト |
| 以前は実行していた品質ゲートのコマンド・`count_pattern`・`required`・`levels` が変わった、ゲートがなくなった（利用者の承認とは別に） | テスト |
| 上のどれにも当たらない | セルフレビュー（`self`）か、対象外（`not_applicable`）で足りる |

- 「その変更記録の範囲」とは、`components` に入っているコンポーネント、`requirements` に入っている要件、`quality_base` に入っている
  台帳・ゲートの定義です。同じブランチの別の変更が足したコンポーネントで、関係のない小さな変更まで重くはしません。
  基準のブランチに取り込むまでは、新設したコンポーネントは「新設」のままなので、そこに手を入れる次の変更にも設計レビューが要ります。
- 優先度を同じ変更の中で `must` から下げても、水準は下がりません（変更の前か後のどちらかで `must` なら、重要として扱います）。
- 基準のブランチと比べられないとき（git の管理下にない、基準のブランチがない）は、重要度を判定できないので、両方とも独立したレビューを必須にします。
- 機械の判定は下限です。公開している入口の変更、台帳に現れない結合の追加、損害の大きい規則の変更は、差分からは見分けられません。
  エージェントは、判定に出なくても独立したレビューを頼みます（`.claude/skills/verify-and-report/SKILL.md` の「レビュー」）。
- **完了を止めるのであって、途中の保存は止めません。** 差し戻しのままコミットできます。`change close` だけが通りません。
- 差し戻しは、重大な指摘を直して、もう一度レビューを受けて合格するまで続きます。指摘に同意できないときは、エージェントが
  自分で `passed` と書くのではなく、利用者が判断します（利用者が見て認めたなら、`passed` と書き、「レビュー」の節に経緯を残す）。
- 「レビュー」の節には、誰が見たか、判定、指摘への対応（直した・直さない理由）を書きます。`change close` は、判定に使った
  水準と理由を「検証結果」に残します。
- これは記録です。受けていないレビューを `passed` と書くことまでは、機械では止められません。値と「レビュー」の節は差分に残るので、
  取り込む前に読めます。
- この項目ができる前に完了した変更記録（`design_review`・`test_review` がないもの）は、そのまま有効です。
  完了済みの記録にこの項目があり、`pending` か `rejected` なら、検査がエラー（`CHG-REVIEW`）にします。

## 品質基盤を変えるとき

品質基盤とは、検査そのものを決めているファイルです。ここを書き換えれば、コードを直さずに検査だけを通せます
（テストのゲートを、何も確かめないコマンドに差し替える、など）。そのため、変更には**人の承認の記録**を求めます。

| 対象 | 例 |
|---|---|
| ゲートの定義、台帳の設定、コンポーネントの台帳 | `trace/gates.toml`、`trace/config.toml`、`trace/components.toml` |
| 検査ツール | `tools/tracekit.py`、`tools/verify.py`、`tools/git-hooks/`、`tools/tests/test_tracekit.py` |
| CI と承認の設定 | `.github/workflows/`、`CODEOWNERS` |
| エージェントの hook・手順・行動規約 | `.claude/settings.json`、`.claude/hooks/`、`.claude/skills/`、`.claude/agents/`、`AGENTS.md`、`CLAUDE.md` |
| プロジェクトで足したもの | `trace/config.toml` の `quality_base`（リンターの設定など） |

```bash
python3 tools/tracekit.py change new --title "型検査を mypy から pyright に替える" --kind chore \
    --quality-base trace/gates.toml
```

- 上のコマンドは、変える範囲を書くだけです。**承認した人（`approved_by`）は、承認を得てから書きます。**
  Claude Code では、エージェントが `approved_by` を Edit で書こうとすると、利用者に確認のダイアログが出ます
  （「変更記録 CHG-003 に、あなたが承認したという記録を書きます。対象: 品質基盤 trace/gates.toml」）。
  許可すれば記録され、以後その範囲の編集は確認なしで通ります。同じ対象について、もう一度は確かめません。
- 確認のダイアログを出せない環境（対話のない実行）では、Claude Code がこの編集を拒みます。自動では承認されません。
- 有効な変更記録の `quality_base` にそのパスがあり、`approved_by` が書かれているときだけ、hook・コミット前の検査・CI を通ります。
- 上の最初の4行は、設定で外せません。
- **導入の途中は、求めません。** ゲートや置き場所を設定し、最初のコンポーネントを宣言している段階だからです。
  導入の途中かどうかは、**変更する前の台帳**（コミット前なら `HEAD`、プルリクエストなら取り込み先との分かれ目）に
  コンポーネントがあるかで決めます。コンポーネントを宣言した台帳を一度コミットすれば、そのあとで手元の台帳を
  空にしても、保護は外れません。
- コンポーネントの台帳も品質基盤です。コンポーネントの追加・分割、依存の追加は、承認を得てから行います。
  新しいコンポーネントは台帳に書くまで `components` に指定できないので、先に `--quality-base trace/components.toml`
  で変更記録を作り、台帳を書いてから、変更記録の `components` に足します。
- 名前を書くだけなので、偽ることはできます。記録は「誰が認めたことになっているか」を差分に残して、
  レビューで見えるようにするためのものです。確実に止めるには、ブランチの保護で、これらのパスに
  コードオーナーのレビューを必須にします（README「チームで使うとき」）。

## 以前あった保証を失うとき（後退の受け入れ）

検査は、いまの台帳が整合しているかだけでなく、**基準のブランチ（`trace/config.toml` の `base_branch`。既定は `main`）と
比べて失われたもの**を見ます。要件やテストを消して台帳だけを整えても、合格にはなりません。

```bash
python3 tools/tracekit.py regress
```

| 見つけるもの | ID の形 | 扱い |
|---|---|---|
| 内容の固まった要件がなくなった・廃止された・状態が戻った（`implemented` → `draft` など） | `REQ-002` | 承認が要る |
| 要件の検証レベル（`verify`）が外された | `REQ-001/verify:integration` | 承認が要る |
| 受け入れ条件がなくなった、確かめるテストが1つもなくなった | `REQ-001/AC-3` | 承認が要る |
| 要件を確かめていたテストファイルがなくなった（別のファイルに移しただけなら数えない） | `tests/unit/test_x.py` | 承認が要る |
| 完了済みの変更記録が消された・書き換えられた | `CHG-001` | 承認が要る |
| 対応の欠落を示す警告が新しく出た（`TEST-UNLINKED`・`COMP-NOREQ`・`TEST-DEPRECATED`・`LEVEL-NOT-RUN`） | `TEST-UNLINKED:tests/unit/test_y.py` | 直すか、承認が要る |
| 受け入れ条件を確かめるテストが減った（まだ残っている） | — | 報告だけ |
| テストが大きく変わった（確かめる文が減った、半分以下になった） | — | 報告だけ |
| 受け入れ条件の文面が変わった（番号は同じ） | — | 報告だけ（前後の文面を載せる） |
| テストの補助ファイル（代用品、共通の準備など。テストのフォルダにある、テストではないファイル）が変わった・なくなった | — | 報告だけ |
| そのほかの警告が新しく出た（粒度など、設計を見直す目安） | — | 報告だけ |

- 基準のブランチが見つからないときは、直前のコミットで代用しません。導入が済んでいれば「比べられない」として不合格にします
  （基準のブランチを消す・別名にするだけで、コミットした後退が見えなくなるのを防ぐため）。
- 以前からある警告は、止めません。警告は件数ではなく1件ずつ見分けるので、1件直して別の1件を増やしても、新しいほうは見つかります。
- 承認が要るものは、変更記録の `accepts` にその ID を書き、承認を得てから `approved_by` を書きます（確認のダイアログが出ます）。
  要件の ID を書けば、その受け入れ条件と、その要件だけを確かめていたテストも含みます。
- 「報告だけ」のものは不合格にしません。テストの中身を抜いても要件IDが残っていれば機械では良し悪しを決められないので、
  人とレビューが読むための一覧に載せます。`main` に取り込む前に、この報告を読んでください。
- テストの変更・削除は、これとは別に、そのテストが確かめている要件が変更記録の `requirements` に入っていることを求めます。

## 範囲が広がったとき

実装の途中で、範囲の外のコンポーネントも変える必要が分かったら、`components` に足すだけで済ませません。
`python3 tools/tracekit.py impact --components …` をやり直し、影響分析と回帰テスト計画を更新します。
設計の骨格が変わる場合は、設計の工程に戻ります。

## どの変更記録が「有効」か

| 場面 | 有効とみなす変更記録 |
|---|---|
| 編集の時点（hook） | 進行中（`active`）のもの |
| 作業を終えるとき（hook）・品質ゲート（`regress`） | 進行中のもの ＋ 基準のブランチから先で追加・更新された完了済みのもの |
| コミット前（`guard --staged`） | 進行中のもの ＋ 同じコミットに含まれる完了済み（`done`）のもの |
| プルリクエスト（`guard --base … --strict`） | そのプルリクエストで追加・更新されたもの（進行中・完了済みのどちらも） |

プルリクエストで条件が厳しくなるのは、閉じ忘れた変更記録が取り込まれたあと、
無関係な変更までその記録の範囲として通ってしまうのを防ぐためです。
1つの変更を複数のプルリクエストに分ける場合は、それぞれのプルリクエストで、変更記録に今回の内容を書き足します。

## 完了の条件

`change close` は、次をすべて満たしたときだけ完了にします。

- 「目的」「変更内容」「台帳に現れない影響の調査」「回帰テスト計画」「レビュー」「不確実な点・残るリスク」が書かれている
- **レビューが済んでいる**（上の「レビュー」）。`design_review`・`test_review` のどちらも、差し戻し（`rejected`）でも
  未実施（`pending`）でもない。独立したレビューが必須の変更では、`passed` である
- 対象の要件が `implemented`（または `deprecated`）になっている
- `tools/verify.py` の全ゲートが PASS か、承認つきの SKIP（区分・理由・承認した人が書かれ、期限を過ぎていない）である。
  必須（`required = true`）のゲートは、SKIP にできない

完了にすると、変更記録の末尾に「検証結果」（実施日、検証した時点のコミット、各ゲートの結果、レビューの水準と判定）が追記されます。
ゲートの結果は、次のように分けて残ります。PASS 以外は、合格ではありません。

| 表示 | 意味 |
|---|---|
| `PASS` | 実行して、合格した |
| `FAIL` | 実行して、失敗した（または、ゲートの外し方が認められない）。完了にできない |
| `SKIP:対象外` | 確かめる対象がない（`skip_kind = "not_applicable"`）。理由と承認した人が残る |
| `SKIP:免除` | 対象はあるが、検証していない（`skip_kind = "waiver"`。承認された例外）。理由・承認した人・期限が残る |
| `UNSET` | 未設定（未導入）。コマンドも理由もない。完了にできない |
| `NOTRUN` | 今回は実行していない（基準のブランチと比べられなかった `regress`、`verify.py --only` で外したゲート） |
