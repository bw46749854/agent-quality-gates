# 要件

要件は1件につき1ファイルで、`REQ-001.md` のように置きます（`REQ-001-order.md` のように続けて名前を足しても構いません）。
書き方の手順は `.claude/skills/define-requirements/SKILL.md`、ひな形は [`_template.md`](_template.md) です。

## 先頭部分（フロントマター）

```
---
id: REQ-001
title: 在庫がある商品を注文できる
status: approved
priority: must
components: [COMP-ORDER, COMP-INVENTORY]
verify: [unit, integration]
---
```

| 項目 | 意味 |
|---|---|
| `id` | `REQ-` と3桁以上の番号。一度付けたら変えない。廃止しても再利用しない |
| `status` | 下の表を参照 |
| `priority` | `must` / `should` / `could` |
| `components` | この要件を実現するコンポーネント（`trace/components.toml` のID）。設計の工程で埋める |
| `verify` | この要件を確かめるテストのレベル（`trace/config.toml` の `[tests]` にある名前）。テスト設計の工程で埋める |

書けるのは `キー: 値` と `キー: [a, b]` の形だけです。

## 状態と、検査が求めるもの

| status | 意味 | 検査が求めるもの |
|---|---|---|
| `draft` | 書きかけ | 書式だけ |
| `approved` | 内容が固まり、実装してよい | 受け入れ条件が1つ以上、`components` と `verify` が埋まっている |
| `implemented` | 実装とテストが済んだ | すべての受け入れ条件にテストがある。`verify` の各レベルにテストがあり、そのレベルを実行するゲートがある。各コンポーネントにコードがある |
| `deprecated` | 廃止した | なし（参照しているテストがあれば警告） |

`draft` 以外の要件のファイルを変えたときは、その要件を変更記録の `requirements` に入れます
（入っていないと、コミット前の検査と CI が止めます）。要件の変更も、影響分析の対象だからです。

## 受け入れ条件

本文に、次の形の箇条書きで書きます。番号は要件の中で一意にし、あとから振り直しません。

```
- **AC-1**: WHEN 在庫数以下の数量で注文する THEN 注文が成立し、在庫が注文数だけ減る
```

`- AC-1: …`（太字でない）、`- **AC-1:** …`（コロンが太字の中）、`1. **AC-1**: …`（番号つき）のように
形が違うと、検査の対象になりません。見落としたまま進まないよう、検査がエラー（`REQ-AC-FORMAT`）にします。

テストからは `REQ-001/AC-1` の形で参照します。この文字列がテストファイルのどこか
（テスト名、コメント、説明文など）に書かれていれば、検査はそのテストを対応づけます。

## 性能などの品質要件

性能・可用性・セキュリティなどの要件も、同じ形で書きます。受け入れ条件には測れる値を書き、
`verify` には対応するテストのレベル（必要なら `trace/config.toml` に `performance` などを追加）を指定します。
