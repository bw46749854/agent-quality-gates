# 要件を定める

成果物: `docs/requirements/REQ-NNN.md`（書式は `docs/requirements/README.md`、ひな形は `_template.md`）

## 手順

1. **既存の要件を読む。** 同じことを言っている要件、今回の依頼と矛盾する要件がないかを確かめる。あれば、新しく作らずに既存の要件を直す。
2. **依頼を、利用者から見た振る舞いに言い換える。** 「〜のAPIを作る」ではなく「利用者が〜できる」。実現方法は書かない。
3. **1つの要件を、1つの目的に絞る。** 目的が2つあるなら2件に分ける。目安は、受け入れ条件が7つを超えたら分割を考える。
4. **受け入れ条件を書く。** 下の「受け入れ条件の書き方」に従う。
5. **あいまいな点を洗い出す。** 下の「確認が要るかの判断」に従い、確認するか、仮定として書く。
6. **優先度（`priority`）を決める。** 破られたときに利用者の損害が大きい要件（お金・在庫・権限・個人情報、主要な業務の流れ）は
   `must`。`must` の要件を定める・受け入れ条件を変える変更には、独立したテストレビューの合格が完了の条件になるので、
   何でも `must` にせず、何でも `should` にもしない。
7. **番号を決めて保存する。** 既存の最大番号の次。`status: draft` で保存する。`components` は設計の工程で、`verify` はテスト設計の工程で埋め、3つがそろったところで `approved` にする（`draft` のあいだは、本番コードを編集できない）。
8. `python3 tools/tracekit.py check --no-matrix` を実行し、書式のエラーがないことを確かめる
   （作業の途中は `--no-matrix` を付ける。マトリクスは生成物で、`change close` が作り直す）。

## 受け入れ条件の書き方

形: `- **AC-n**: WHEN （条件・操作） THEN （外から観察できる結果）`

- **結果は外から観察できること。** 「正しく処理される」「適切に検証する」は観察できない。「注文が拒否され、在庫数が変わらない」は観察できる。
- **1つの条件に、1つの場面。** 「かつ」「または」で場面が増えるなら分ける。
- **次の観点を一通り検討する。** 当てはまらないものは書かなくてよいが、検討はする。
  - 正常な場合
  - 異常な入力（空、範囲外、形式の違い）
  - 境界（ちょうどの値、1つ超えた値、0、上限）
  - 状態（すでに処理済み、存在しない対象、順序が逆）
  - 外部の失敗（保存に失敗、相手が応答しない）
  - 失敗したときに**変わらないこと**（途中まで進んだ処理が残らない）
  - **常に成り立つべきこと**（不変条件: ID が重複しない、予約が重ならない、在庫が負にならない、など）。
    「当たり前」として書かずにおくと、テストも書かれない。受け入れ条件として書く
- **数や時間は値で書く。** 「速く」ではなく「1秒以内に」。値が決まっていなければ、確認するか仮定として書く。

書き終えたら、各条件について「これが満たされているかを確かめるテストを、実装を知らずに書けるか」を自問する。書けないなら、条件がまだあいまい。

## 確認が要るかの判断

- **確認する**: 解釈によって作るものが変わる。あとから直すと既存のデータや利用者に影響する。お金・権限・個人情報に関わる。
- **仮定として書いて進める**: どちらに決めても簡単に直せる。業界や既存の実装に、明らかな慣例がある。

両方に当てはまるとき（解釈で作るものは変わるが、直すのは簡単）は、**確認する**。
利用者がその場にいない実行では、勧める案を仮定として進め、**報告の冒頭に「確認が要る点」として**、選択肢・勧め・
違っていた場合に直す所を書く（本文に埋もれさせない）。

仮定は「仮定・未解決事項」に、何を仮定したかと、違っていた場合に何を直すかを書く。

## 既存の要件を変えるとき

- 受け入れ条件を足すときは、新しい番号を使う。既存の番号は振り直さない（テストが参照しているため）。
- 受け入れ条件の意味を変えるときは、それを参照しているテストを `grep -rn "REQ-001/AC-2"` で探し、影響分析の対象に含める。
- 要件を廃止するときは、ファイルを消さずに `status: deprecated` にする。

## 既存のコードから要件を起こすとき

要件が書かれていない既存のシステム（導入の直後、再構築の前）では、コードとテストから要件を起こす。

- **コードから読み取った仕様と、確認済みの要件を区別する。** コードがそう動いていることは、そう動くべきことの証明ではない
  （不具合かもしれないし、もう要らない経緯かもしれない）。読み取っただけのものは、「仮定・未解決事項」に
  「既存の動作から読み取った。未確認」と書き、利用者に確かめるまで `draft` のままにするか、確かめる点として報告する。
- **理由の分からない処理を、不要と決めつけない。** 特定の相手だけの割引、例外的な分岐、順序への依存は、
  どこにも書かれていない業務上の約束であることが多い。消す・変える前に、利用者に聞く。

## 不具合の修正のとき

不具合は「どの受け入れ条件が破られているか」で表す。

- 該当する受け入れ条件がある → その条件のテストが、なぜ不具合を検出できなかったかを調べる（テスト設計の工程で直す）。
- 該当する受け入れ条件がない → 要件の書き漏れ。受け入れ条件を足す。
