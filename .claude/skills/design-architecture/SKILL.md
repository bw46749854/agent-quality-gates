# 設計する

成果物:
- `trace/components.toml`（境界と依存の向きの正本。検査が使う）
- `docs/architecture.md`（なぜその構成かの説明）
- 要件ファイルの `components`
- 骨格を変える判断をしたときは `docs/decisions/NNNN-*.md`

## 手順

1. **いまの構成を読む。** `trace/components.toml`、`docs/architecture.md`、`docs/traceability.md` の逆引き表。既存の構成を理解しないまま、新しい構造を足さない。
2. **要件を、既存のコンポーネントに割り当ててみる。** 各受け入れ条件について「この振る舞いを保証する責任は、どのコンポーネントにあるか」を決める。
3. **割り当てられないものがあれば、境界を見直す。** 下の「境界の決め方」に従う。
4. **依存の向きを決める。** 下の「依存の決め方」に従う。
5. **台帳を変える必要があるなら、先に利用者の承認を得る。** `trace/components.toml` は品質基盤で、承認の記録がないと
   hook が編集を止める。変える内容（足すコンポーネント、足す依存、変える境界）と、選ばなかった案を利用者に示す。
   変更記録を作り（進行中の変更記録があれば、その先頭部分に `quality_base: [trace/components.toml]` を足す）、
   承認が得られたら、`approved_by:` に承認した人の名前を Edit で書く（Claude Code では、このとき利用者に確認のダイアログが出る）。
   ```bash
   python3 tools/tracekit.py change new --title "（何をするか）" --kind feature --requirements REQ-001 \
       --quality-base trace/components.toml
   ```
   新しいコンポーネントは、台帳に書いたあとで、変更記録の `components` に足す（影響分析の工程で行う）。
   導入の途中（コンポーネントを宣言した台帳を、まだ一度もコミットしていない）なら、この手順は要らない。
6. **台帳と設計書を更新する。** `trace/components.toml` にコンポーネント（`id`・`name`・`responsibility`・`paths`・`depends_on`・`reference_patterns`）を書き、`docs/architecture.md` の該当する節を直し、要件の `components` を埋める。まだコードがないコンポーネントは `status = "planned"` にする。
7. **`python3 tools/tracekit.py check` を実行する。** 循環、重なり、知らない依存先のエラーと、粒度の警告（`GRAN-COARSE`、`GRAN-SCATTERED`）を確かめる。
8. **`design-reviewer` サブエージェントにレビューを頼む**（コンポーネント・依存・公開インターフェースを変えたとき）。指摘を直すか、直さない理由を設計判断として残す。
9. **レビューを受けて台帳を直した場合は、承認を得た内容から変わった点を利用者に伝える。**

設計を変えない場合（既存のコンポーネントの中だけで済む場合）は、2 と 7 を行い、「設計は変えない。理由: …」と変更記録に書けば足りる。

## 境界の決め方

コンポーネントは、**トレースする単位**であり、**変更の影響を止める単位**でもある。次の問いで決める。

- **一緒に変わるものを、一緒に置く。** ある要求が変わったとき、手を入れる場所が1つのコンポーネントに収まるか。
- **別の理由で変わるものを、分ける。** 1つのコンポーネントの「変わる理由」を1文で言えるか。「と」でつながるなら、分割を考える。
- **責務を、知識と保証で言う。** 「〜を知っていて、〜を保証する」。「〜関連の処理」「ユーティリティ」「共通」は責務ではない。

粒度の両側の失敗を、台帳の数字で確かめる。

| 兆候 | 意味 | 対処 |
|---|---|---|
| どの要件も同じコンポーネントに結びつく。`GRAN-COARSE` の警告 | 粗すぎる。変更の影響を絞り込めない | 変わる理由ごとに分ける |
| 1つの要件が多くのコンポーネントにまたがる。`GRAN-SCATTERED` の警告 | 細かすぎるか、責務が散らばっている | まとめる。または要件を分ける |
| 1つの変更で、いつも同じ2つのコンポーネントを一緒に直している | 境界の位置がずれている | 一緒に変わる部分を片方に寄せる |
| 要件のないコンポーネントがある（`COMP-NOREQ`） | 作りすぎか、要件の書き漏れ | 消すか、要件を書く |

迷ったら、粗いほうから始める。分けるのは、分ける理由（別々に変わった、別々にテストしたい、別の人が持つ）が実際に現れてからでよい。

## 依存の決め方

- **循環させない。** A が B を使い、B が A を使うなら、境界が間違っているか、共通の部分を第三のコンポーネントに出す必要がある。
- **業務の規則を持つ側が、具体的な仕組みに直接依存しない。** 保存先・通信・画面・フレームワークは外側に置き、業務の側が決めた形（インターフェース）に、外側が合わせる。
- **相手の内部に触れない。** ほかのコンポーネントを使うときは、相手が公開している入口だけを使う。入口は `docs/architecture.md` の「主要なインターフェース」に書く。
- **使わない機能に依存しない。** 相手の入口が大きすぎて、使わない部分の変更に巻き込まれるなら、入口を用途ごとに分ける。
- **依存を足すときは、理由を書く。** 「動かすために必要だった」は理由にならない。その依存が、どの要件のどの振る舞いのために必要かを書く。

## 抽象を足すかどうか

インターフェースや層を足すのは、次のどれかが**いま**当てはまるときだけにする。

- 差し替える相手が、実際に2つ以上ある（本番の保存先と、テスト用の代用品を含む）
- 依存の向きを逆にしないと、業務の規則が具体的な仕組みに引きずられる
- 相手が別の理由・別の速さで変わり、その変更から守りたい

「将来必要になるかもしれない」だけでは足さない。足さなかった判断も、迷ったなら `docs/decisions/` に残す。

## reference_patterns の書き方

「ほかのコンポーネントがこのコンポーネントを参照するとき、コードの1行に現れる形」を正規表現で書く。

```toml
# Python
reference_patterns = ['^\s*(from|import)\s+order\b']
# TypeScript / JavaScript
reference_patterns = ['from\s+"(@app|\.\.?(/\.\.)*)/order[/"]']
# Go
reference_patterns = ['"example\.com/app/order[/"]']
# Java / Kotlin
reference_patterns = ['^\s*import\s+com\.example\.order\.']
# C#
reference_patterns = ['^\s*using\s+App\.Order\b']
```

これは言語に依らない簡易な検査で、動的な参照などは拾えない。厳密に調べる専用の道具があれば、
`trace/gates.toml` の `architecture` ゲートに設定する（`adapters/README.md`）。
