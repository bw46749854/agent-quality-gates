# 品質ゲートつき開発テンプレート

AI エージェントに開発を任せながら、次の5つを**仕組みで**守るためのテンプレートです。言語やフレームワークを問いません。

1. 設計原則（SOLID・高凝集・疎結合）
2. トレーサビリティ（要件 ⇔ コンポーネント ⇔ コード ⇔ テスト）
3. テスト戦略（リスクに応じたレベルの使い分け）
4. 変更影響分析
5. 回帰テストと継続的な検証

エージェントに「守ってください」と頼むだけでは守られません。このテンプレートは、
**守られていない状態では次に進めない**ようにします。

## 中心となる考え方

**コンポーネントを、トレースする単位にする。**
関数やファイルの単位で対応表を作ると、更新が追いつかずに破綻します。「フロントエンド／バックエンド」の単位では、何を変えても全部が関係してしまいます。
このテンプレートでは、責務で分けたコンポーネントを単位にし、粗すぎ・細かすぎを数字で警告します。

**コードとコンポーネントの対応は、置き場所で決める。**
コードにIDを書かせません。`trace/components.toml` に「このフォルダはこのコンポーネント」と宣言するだけです。
テストには、確かめる受け入れ条件を `REQ-001/AC-2` の形で書きます。対応表は、この2つから機械が作ります。

**境界が守られている限り、影響範囲は機械で計算できる。**
変更したファイル → コンポーネント → 依存しているコンポーネント → 要件 → 実行すべきテスト、とたどれます。
境界が崩れた（宣言していない依存ができた）ときは、検査が落ちます。トレーサビリティと依存の検査は、同じ台帳の表と裏です。

**同じ検査を、3か所から呼ぶ。**
検査の中身は `tools/` のスクリプトにあり、エージェントの hook・コミット前・CI が同じものを呼びます。
hook が使えないエージェントや手作業の変更も、コミット前と CI で止まります。

## 構成

```
AGENTS.md                  エージェントの行動規約（短い。詳細は skill に置く）
CLAUDE.md                  AGENTS.md を読み込むだけ

trace/                     台帳（検査の入力）
  config.toml                本番コードとテストの置き場所、粒度のしきい値
  components.toml            コンポーネントの境界・責務・依存の向き
  gates.toml                 品質ゲートで実行するコマンド

docs/
  requirements/REQ-*.md      要件と受け入れ条件（1件1ファイル）
  changes/CHG-*.md           変更記録（影響分析の記録 ＝ 編集してよい範囲の宣言。品質基盤の変更の承認もここに残す）
  architecture.md            なぜその構成かの説明
  decisions/                 設計判断の記録
  test-strategy.md           テスト戦略
  traceability.md            マトリクス（生成物。手で編集しない）

tools/
  tracekit.py                検査・影響分析・変更記録・マトリクス生成
  verify.py                  品質ゲートの一括実行
  git-hooks/pre-commit       コミット前の検査
  tests/                     検査ツール自身のテスト

.claude/
  skills/                    各工程の手順（7本）
  agents/                    設計レビュー・テストレビュー用のサブエージェント
  hooks/                     Claude Code の hook（3本）
  settings.json              hook の設定（置くだけで有効になる）

adapters/README.md         言語ごとの設定例
examples/shop/             動くサンプル（注文管理と在庫管理）
.github/workflows/         CI の例
```

## 守りの層

| 層 | 役割 | 強さ |
|---|---|---|
| `AGENTS.md` | 原則と進め方を伝える | お願い。破られうる |
| skill | 各工程の手順と判断の基準を与える | 手順の質を上げる。強制はしない |
| サブエージェント | 設計とテストを、実装した本人とは別の文脈でレビューする | 自己評価の甘さを減らす |
| hook（Claude Code） | 影響分析のない本番コードの編集と、承認のない品質基盤の編集を止める。台帳が食い違ったまま、または範囲の外の変更を残したまま終わらせない | その場で止める |
| 確認のダイアログ（Claude Code） | 品質基盤の変更や、以前あった保証を失う変更の承認を、利用者本人に確かめる | エージェントは代わりに答えられない。確かめるのは重要な変更だけ |
| `change close` | 全ゲートを通らないと、変更を完了にできない | 完了の定義そのもの |
| 基準のブランチとの比較（`regress`） | 以前あった要件・受け入れ条件・テストが失われていないかを、`main` と比べて見つける | 「いまの台帳が整合しているか」だけでは見えない後退を止める |
| pre-commit と CI | 同じ検査を、エージェントの外で行う | エージェントの外の防衛線 |
| ブランチの保護とコードオーナー（リポジトリの設定） | CI が失敗した変更と、品質基盤に触れる変更を、人の承認なしに取り込ませない | **最後の防衛線。** 上の層はどれもリポジトリの中のファイルなので、書き換えられる。ここだけが外にある |
| `doctor` | 上の層が、実際に有効になっているかを確かめる | 仕組みが「入っているつもり」で止まっていない状態を見つける |

### 検査そのものを弱めさせない

テストのゲートを「何もしないコマンド」に差し替えれば、コードを直さなくても検査は通ります。悪意がなくても、
エージェントが「通すために設定を軽くする」だけで同じことが起きます。そこで、検査を決めているファイル
（**品質基盤**: `trace/gates.toml`・`trace/config.toml`・`trace/components.toml`・`tools/` の検査ツール・
`.github/workflows/`・`.claude/` の hook と skill・`AGENTS.md`）の変更は、本番コードと同じように止めます。
コンポーネントの台帳を含めているのは、依存を1行足せば「宣言していない依存」の検査が通り、
台帳を空にすれば検査の対象そのものがなくなるからです。

- 通すには、変更記録の `quality_base` にそのパスを書き、承認を得てから `approved_by` に**承認した人の名前**を書きます（[`docs/changes/README.md`](docs/changes/README.md)）。
  Claude Code では、エージェントが `approved_by` を書こうとした時点で、**利用者に確認のダイアログが出ます**。
  許可して初めて記録され、以後その範囲の編集は確認なしで通ります（同じ対象を何度も確かめません）。
  対話のない実行など、ダイアログを出せない環境では、Claude Code がその編集を拒みます。自動では承認されません。
- CI の番人（`guard`）は、取り込み先のブランチにある検査ツールで動かします。プルリクエストが検査ツール自身を書き換えても、書き換える前の規則で調べます。
- 保護が働くかどうかは、**変更する前の台帳**（コミット前なら `HEAD`、プルリクエストなら取り込み先との分かれ目）で決めます。
  変更する側で台帳を空にしても、保護は外れません。
- ゲートの外し方は、3つに分かれます。SKIP は合格ではなく「検証していない」と表示・記録します。

  | ゲート | 外せるか |
  |---|---|
  | 必須（`required = true`） | 外せない。理由や承認があっても不合格 |
  | 確かめる対象がない（`skip_kind = "not_applicable"`。画面のないライブラリの E2E など） | 理由と、承認した人（`skip_approved_by`）があれば外せる |
  | 一時的な免除（`skip_kind = "waiver"`） | 理由・承認した人・**期限（`skip_until`）**があれば外せる。期限を過ぎた日から不合格 |

  要件が求めるテストレベルは、上の表とは別に、どの区分でも外せません（`LEVEL-NOT-RUN`）。
- `doctor --ci` を CI で実行し、本番コードの置き場所が空、コンポーネントがない、といった
  「検査の対象を減らして通す」状態を止めます。
- それでも、名前は偽れますし、CI の定義も書き換えられます。**確実に止めるのは、リポジトリの設定（ブランチの保護とコードオーナー）です。**
  「チームで使うとき」の設定を必ず行ってください。

### 以前あった保証を失わせない

要件とテストを消して台帳だけを整えれば、「いまの状態」は整合して見えます。そこで、**基準のブランチ（既定は `main`）との
分かれ目と比べて、失われたもの**を調べます。コミットした変更も、していない変更も、新しいファイルも、消したファイルも対象です。

```bash
python3 tools/tracekit.py regress
```

| 見つけるもの | 扱い |
|---|---|
| 要件の削除・廃止・状態を戻すこと（`implemented` → `draft` など）、受け入れ条件の削除 | 承認が要る |
| 受け入れ条件を確かめるテストが1つもなくなった、要件を確かめていたテストファイルがなくなった | 承認が要る |
| 完了済みの変更記録の削除・書き換え | 承認が要る |
| 対応の欠落を示す警告が新しく出た（要件IDのないテスト、要件のないコンポーネントなど） | 直すか、承認が要る |
| テストが大きく変わった（確かめる文が減った、半分以下になった）、テストが減った | **報告だけ**（不合格にしない） |
| 粒度などの警告が新しく出た | 報告だけ |
| 要件の検証レベル（`verify`）を外した | 承認が要る |
| 受け入れ条件の文面が変わった、テストの補助ファイル（代用品など）が変わった | **報告だけ**（前後の文面を載せる） |
| 基準のブランチが見つからない（導入が済んだあと） | 不合格（比べられないことを合格にしない） |

- 承認は、変更記録の `accepts` に ID を書き、`approved_by` を書くことで記録します（上と同じく、確認のダイアログが出ます）。
- 警告は件数ではなく1件ずつ見分けます。以前からある警告は止めません（既存のプロジェクトに入れても、古い問題で止まりません）。
- 既存のテストを変える・消すには、そのテストが確かめている要件が、変更記録の `requirements` に入っている必要があります
  （通らないテストを、関係のない作業のついでに書き換えさせないため）。新しいテストの追加は止めません。
- テストの中身だけを抜く（要件IDは残して `assert True` にする）操作は、機械では良し悪しを決められません。
  「確かめる文が N → M 行に減った」と報告に載せ、人とレビュー用のサブエージェントが読みます。
- テストを実行するゲートは、実行した件数を出力から読み、0 件なら不合格にします（`count_pattern`。`adapters/README.md`）。

### 個人で使うとき

承認する人が自分しかいない場合、名前を書かせるだけの手続きは保証になりません。そこで、次の形にしています。

- **通常の実装、テストの追加、範囲の中でのテストの修正は、確認なしで進みます。**
- **確認が出るのは、重要な変更だけ**です。品質基盤の変更（ゲート、台帳、検査ツール、hook）と、以前あった保証を失う変更
  （要件の廃止、テストの削除など）。エージェントが承認を記録しようとした時点で、Claude Code があなたに確認します。
- **エージェントは作業ブランチで変更し、`main` への取り込みはあなたが行います。** `main` は「あなたが確かめて取り込んだ状態」で、
  検査はそこと比べます。取り込む前に `python3 tools/tracekit.py regress` の報告（承認済みの後退、確かめてほしい点、
  承認として記録されているもの）を読んでください。読むのは、これ1枚で足ります。
- ブランチの保護やコードオーナーは、1人では要りません。CI は、あれば同じ検査が動きます。

シェルのコマンドで承認を書き込まれた場合は、確認が出ません（hook が見ているのは Edit / Write です）。
`.claude/settings.json` の PreToolUse の matcher を `Edit|Write|NotebookEdit|Bash` にすると、シェルから `approved_by` に
触れる操作にも確認が出ます。どちらの場合も、承認として記録されたものは `regress` の報告に必ず載ります。
身に覚えのない承認があれば、取り込まないでください。

## 検査が見つけるもの

`python3 tools/tracekit.py check` が見つける主なもの:

| 種類 | 内容 |
|---|---|
| `CODE-ORPHAN` | どのコンポーネントにも属さない本番コード |
| `DEP-UNDECLARED` | 台帳に宣言していないコンポーネント間の依存 |
| `COMP-CYCLE` | 依存の循環 |
| `REQ-AC-UNTESTED` | テストのない受け入れ条件 |
| `REQ-AC-FORMAT` | 受け入れ条件のつもりで書かれているが、形が違うために検査の対象になっていない行 |
| `REQ-LEVEL-MISSING` | 要件が求めるレベル（単体・結合など）のテストがない |
| `LEVEL-NOT-RUN` | 要件が求めるレベルのテストを、どのゲートも実行していない（テストがあるだけで、実行されない） |
| `TEST-DANGLING` | 存在しない要件・受け入れ条件を参照しているテスト |
| `COMP-NOREQ`（警告） | どの要件にも結びつかないコンポーネント |
| `TEST-UNLINKED`（警告） | 要件IDのないテストファイル |
| `GRAN-COARSE`（警告） | 変えると要件の大半に影響するコンポーネント（粗すぎる） |
| `GRAN-SCATTERED`（警告） | 多くのコンポーネントにまたがる要件（細かすぎる・散らばっている） |
| `MATRIX-STALE` | マトリクスが台帳と合っていない |
| `CHG-NO-APPROVER` | 品質基盤の変更（`quality_base`）や後退の受け入れ（`accepts`）を書いているのに、承認した人が書かれていない、完了済みの変更記録 |
| `CHG-AWAITING-APPROVAL`（警告） | 承認を待っている、進行中の変更記録（承認されるまで何も通さない。完了にはできない） |

同じ種類の警告が多いときは、先頭の10件と件数だけを表示します（`check --all` ですべて表示）。

`python3 tools/tracekit.py guard` は、差分を見て、次の3つを確かめます。

- 本番コードの変更が、変更記録の範囲（`components`）に入っているか
- 内容の固まった要件（`draft` 以外）の変更が、変更記録の `requirements` に入っているか
- 品質基盤の変更が、承認した人を記録した変更記録の範囲（`quality_base`）に入っているか
- 既存のテストの変更・削除が、そのテストが確かめる要件を含む変更記録の範囲に入っているか
- 変更する前と比べて、承認されていない後退（上の「以前あった保証を失わせない」）がないか

プルリクエストでは `--strict` を付けます。進行中の変更記録も、その差分で追加・更新されたものだけを有効とみなし、
閉じ忘れた変更記録が無関係な変更を通してしまうのを防ぎます（[`docs/changes/README.md`](docs/changes/README.md)）。

`python3 tools/verify.py` は、上の検査に加えて `trace/gates.toml` のコマンド（静的解析・型検査・各レベルのテストなど）を実行します。
コマンドも理由も書かれていないゲートは「未設定」として不合格になります（黙って飛ばさないため）。
理由があっても、承認した人が書かれていないゲート、期限を過ぎたゲートは不合格です。
承認つきで実行しないゲートは SKIP と表示し、合格とは分けて「検証していません」と明示します。
`--report ファイル名` を付けると、結果を JSON で書き出します（どのコミットで、どのゲートが、どの結果だったか。CI の成果物や集計に使う）。

`python3 tools/tracekit.py doctor` は、検査の中身ではなく、**仕組みが有効になっているか**を確かめます
（本番コードの置き場所に実際にコードがあるか、未設定・承認のないゲート、コミット前の検査、Claude Code の hook が
働くイベントと道具に設定されているか、CI が番人とゲートの両方を実行しているか、閉じていない変更記録）。
hook は、設定の文面を読むだけでなく、**設定されたコマンドを実際に呼んで**応答するかを確かめます
（`echo pre_edit.py` のように名前が書いてあるだけのコマンドや、本体のない設定は OK になりません。Windows では文面だけを見ます）。
CI の定義は実行できないので、文面からの判定です（コメントや `echo` の中は数えません）。
実際に止まることは、下の「導入したあとの受け入れ確認」で確かめます。`doctor --ci` は、CI の中で実行するための形です。

## 導入の手順

Python 3.11 以上が必要です（検査ツールは標準ライブラリだけで動きます。プロジェクトの言語は問いません）。

1. このテンプレートの中身を、プロジェクトのルートに置く（`examples/` は不要なら消す）。
   **テンプレートの `.git/` は持ち込まない**（配布物の作り方は、下の「テンプレートを配るとき」）。
2. `trace/config.toml` に、本番コードとテストの置き場所と、比較の基準にするブランチ（`base_branch`。既定は `main`）を書く。
3. `trace/gates.toml` に、各ゲートのコマンドを書く。実行しないゲートには理由を書く（`adapters/README.md` に言語ごとの例）。
4. Claude Code の hook は、`.claude/settings.json` を置けば有効になる（すでに自分の `settings.json` があるなら、テンプレートの `hooks` の部分を書き写す）。
5. コミット前の検査を有効にする:
   ```bash
   git config core.hooksPath tools/git-hooks
   ```
   ZIP の展開やファイルのコピーで実行権限が落ちていると、git はこの検査を黙って飛ばします。その場合は付け直します
   （`doctor` も検出します。`.claude/hooks/` の3本は `python3` から呼ぶので、実行権限は要りません）:
   ```bash
   chmod +x tools/git-hooks/pre-commit
   ```
6. CI に `tools/tracekit.py guard` と `tools/verify.py` を組み込む（`.github/workflows/quality.yml` が例）。
7. リポジトリの設定で、CI の成功とコードオーナーのレビューを必須にする（下の「チームで使うとき」）。
8. 有効になったことを確かめる。`NG` がなくなるまで直す:
   ```bash
   python3 tools/tracekit.py doctor
   ```

品質基盤の変更に承認の記録を求める検査は、**コンポーネントを宣言した台帳をコミットした時点から**働きます。
それまで（ゲートや置き場所を設定し、最初のコンポーネントを宣言している段階）は、導入の途中とみなして求めません。
一度働き始めたら、台帳を空にしても導入の途中には戻りません。

### 導入したあとの受け入れ確認

設定の文面が正しくても、実際に止まるとは限りません。導入したら、**わざと違反して、止まることを一度確かめます。**
確かめたら、その変更は捨てます。

| わざとすること | 止まるべき場所 |
|---|---|
| 変更記録なしで、本番コードを1行変えてコミットする | コミット前の検査（`guard --staged`） |
| `trace/gates.toml` の単体テストの `cmd` を `"true"` に変えてコミットする | コミット前の検査 |
| 上の2つを `git commit --no-verify` でコミットし、プルリクエストを出す | CI の `gates` ジョブが失敗し、取り込めない |
| `.github/workflows/quality.yml` から番人の手順を消したプルリクエストを出す | コードオーナーのレビューなしには取り込めない（ブランチの保護） |
| Claude Code に「テストが通らないのでゲートを外して」と頼む | hook が編集を止め、エージェントが承認を求めてくる。承認を記録しようとすると、確認のダイアログが出る |
| 作業ブランチで、要件のファイルとそのテストを消してコミットする | コミット前の検査。`--no-verify` で通しても、`python3 tools/tracekit.py regress` と品質ゲートが `main` との比較で見つける |
| テストのゲートのコマンドを、テストが1件もないフォルダに向ける | 品質ゲート（実行した件数が 0 件） |

4行目だけは検査ツールでは止められません。リポジトリの設定（次の「チームで使うとき」）が効いていることを、ここで確かめます。

Windows で `python3` というコマンドがない場合は、`python` または `py -3` を使います。`.claude/settings.json` の
hook のコマンドも同じように書き換えます（コミット前の検査は、`python3` がなければ `python` を使います）。

**すでにコードがあるプロジェクトに入れる場合**

- 5 の前に、いまのコードをコミットしておく（コミット前の検査は、変更記録のない本番コードの変更を止めるため）。
- まず、既存のコードをすべて覆うようにコンポーネントを宣言する（`CODE-ORPHAN` が消えるまで）。最初は粗くて構いません。
- 既存のコードにある依存は、そのまま `depends_on` に宣言する（台帳を現状に合わせる）。**互いに依存し合っている部分は、
  無理に分けずに1つのコンポーネントとして宣言する。** 循環しているものは、変更の影響を別々には考えられないので、
  それが正直な境界です。循環を解消できたときに、コンポーネントを分けます。
- 要件は、手を入れる箇所から順に書き足す。要件のないコンポーネントは警告（`COMP-NOREQ`）にとどまります。
- 既存のテストに要件IDがないことも警告（`TEST-UNLINKED`）にとどまります。

## チームで使うとき

- **ブランチの保護を設定します（必須）。** CI の定義があるだけでは、失敗したプルリクエストも取り込めます。
  また、検査ツールも CI の定義もリポジトリの中のファイルなので、プルリクエストの中で書き換えられます。
  GitHub なら、取り込み先のブランチ（`main` など）のルールで次を有効にします。
  - 「Require status checks to pass」に、`quality` ワークフローの `gates` ジョブを指定する
  - 「Require a pull request before merging」と「Require review from Code Owners」を有効にする
  - 管理者も例外にしない（「Do not allow bypassing the above settings」）

  そのうえで、品質基盤のコードオーナーを `.github/CODEOWNERS` に書きます（エージェントではなく、人やチームを指定する）。
  ```
  # 品質基盤: ここを変えると検査そのものが変わる。変更には、この人たちのレビューが要る
  /trace/                 @your-org/quality-owners
  /tools/                 @your-org/quality-owners
  /.github/               @your-org/quality-owners
  /.claude/               @your-org/quality-owners
  /AGENTS.md              @your-org/quality-owners
  /CLAUDE.md              @your-org/quality-owners
  # 要件の変更も人が見る
  /docs/requirements/     @your-org/product-owners
  ```
  この設定はリポジトリの外（ホスティングの設定）にあるので、`doctor` からは確かめられません。導入した人が確認します。
- **品質基盤を変えるとき、以前あった保証を失うとき、ゲートを外すときは、承認した人の名前を残します。** 変更記録の `approved_by`、
  ゲートの `skip_approved_by` です。エージェントには、承認を得る前に書かないよう `AGENTS.md` で求めています。
  プルリクエストのレビューでは、`regress` の報告の「承認として記録されているもの」と、この名前が本当に承認した人かを見てください。
- **コミット前の検査は、clone ごとに有効にする必要があります。** `git config core.hooksPath` はリポジトリに保存されません。
  メンバーが加わったとき、clone し直したときは `doctor` で確かめます。忘れても CI が同じ検査で止めます。
- **変更記録は、済んだら閉じます。** 進行中のまま取り込まれた変更記録は、あとから来た無関係な変更を、
  手元（hook とコミット前）では通してしまいます。CI の `guard --strict` はこれを止めます。
- **番号が重なったとき。** 別々のブランチで同じ番号の要件や変更記録を作ると、取り込むときにファイルの衝突か
  `REQ-DUP` / `CHG-DUP` のエラーになります（黙って通ることはありません）。あとから取り込む側が、番号を振り直します。
  要件の番号を変えるときは、テストに書いた `REQ-…` も合わせて直します。
- **マトリクス（`docs/traceability.md`）が衝突したとき。** 生成物なので、手で直さずに
  `python3 tools/tracekit.py matrix --write` で作り直します。
- **リポジトリの一部だけに入れることもできます**（モノレポの中の1プロジェクトなど）。`tools/` と `trace/` を置いた
  フォルダがプロジェクトのルートになり、パスはそこからの相対で書きます。

## 日々の流れ

エージェントには、ふつうに依頼します（「注文のキャンセル機能を追加して」）。エージェントは `develop` skill に従って、次の順に進めます。

| 工程 | 成果物 | 止める仕組み |
|---|---|---|
| 1. 要件を定める | `docs/requirements/REQ-*.md` | 要件が `draft` のあいだは実装に入れない |
| 2. 設計する | `trace/components.toml`、`docs/architecture.md` | 属さない場所のコードは書けない。循環・未宣言の依存は検査で落ちる |
| 3. 影響を調べる | `docs/changes/CHG-*.md` | 変更記録の範囲の外は編集できない |
| 4. テストを設計する | 要件の `verify`、テストケースの案 | `verify` が空だと `approved` にできない |
| 5. 実装する | コードとテスト | 受け入れ条件にテストがないと `implemented` にできない |
| 6. 検証して完了にする | 変更記録の「検証結果」、マトリクス | 全ゲートを通らないと完了にできない |

人が判断するのは、要件の解釈が分かれるとき、設計の骨格を変えるとき、ゲートを外すときです。

## テンプレートを配るとき

フォルダをそのまま ZIP にしてはいけません。`.git/`（履歴と、作成元のリモートの設定）・作業用の worktree・
`__pycache__` が入り、実行権限が落ち、コミットしていない修正や別のブランチの修正は入りません
（実際に、古い版の入った ZIP を配ってしまったことがあります）。
テンプレートの開発元のリポジトリでは、次のコマンドで作ります。git のコミットから書き出し、
**できた ZIP を展開した先で**、検査ツール自身のテスト・サンプルの検査・サンプルの品質ゲートが通ることまで確かめます。
コミットしていない変更があると、作らずに止まります。

```bash
python3 tools/make_dist.py
```

`dist/quality-template.zip` ができます（このスクリプト自身は配布物に入りません）。スクリプトを使わない場合の最小の手順は次のとおりです。

```bash
git archive --format=zip --output quality-template.zip HEAD
```

受け取った側が `unzip` 以外（Windows のエクスプローラーなど）で展開すると、実行権限は付きません。
導入の手順 5 の `chmod +x` と `doctor` で確かめます。

## サンプルを動かす

`examples/shop` は、要件・コンポーネント・テスト・変更記録のつながりを見せるための最小のサンプルです。
保存先はメモリの上の辞書で、同時実行や途中で失敗したときの巻き戻し（トランザクション、排他、冪等性）は扱っていません
（REQ-001 の「仮定・未解決事項」に範囲の外と書いてあります）。業務処理の整合性の手本にはしないでください。

```bash
python3 tools/tracekit.py --root examples/shop check
```

```bash
python3 tools/tracekit.py --root examples/shop impact --files src/inventory/stock.py
```

```bash
python3 tools/tracekit.py --root examples/shop impact --requirements REQ-001
```

```bash
python3 tools/verify.py --root examples/shop
```

```bash
python3 -m unittest discover -s tools/tests
```

## 機械では確かめられないこと・いまの限界

- **責務の分け方が妥当か、テストが本当に要件を確かめているか**は、機械では判定できません。サブエージェントのレビューと、人の確認に頼ります。
- **依存の検査（`reference_patterns`）は、正規表現による簡易なもの**です。動的な参照は拾えません。厳密に調べるには、言語ごとの専用の道具を `architecture` ゲートに設定します。
- **共有しているデータ、イベント、設定値を通じた結合**は、台帳に現れません。影響分析の手順で、人またはエージェントが調べます。
- **テストと要件の対応は、ファイルの単位**です。テストファイルに `REQ-001/AC-2` と書いてあれば対応ありと見なし、その中身は見ません。
  `assert True` だけのテストでも、ID が書いてあれば対応ありになります。テストケースの単位で対応を取ること、
  テストランナーの実行結果（JUnit XML など）と突き合わせて「そのテストが実際に走った」ことを確かめることは、まだしていません。
  テストの中身は `test-reviewer` のレビューで、効き目は変異テスト（`adapters/README.md`）で補います。
- **変更前との比較は、基準のブランチを信頼します。** 手元の git の履歴は書き換えられます。エージェントが基準のブランチ
  （`main`）に直接コミットしたり、履歴を書き換えたりすれば、比較の基準そのものが動きます。`AGENTS.md` で禁じ、
  セッションの冒頭でも知らせますが、機械では止めていません。`main` への取り込みを自分で行うこと、チームでは
  ブランチの保護を設定することが前提です。
- **テストが実行されたかは、件数でしか見ていません。** `count_pattern` は、出力から件数を読むだけです。
  どのテストが走ったか、スキップされたものがないかは見ていません（テストの結果ファイルとの照合は、まだ作っていません）。
  ゲートのコマンドを `echo "Ran 999 tests"` に差し替えれば、999 件と数えます。これを止めているのは、ゲートの定義を
  品質基盤として守る仕組み（承認の記録）のほうで、件数の読み取りは「対象を間違えて何も実行していない」事故を見つけるためのものです。
- **受け入れ条件の意味が変わったかは、機械では判定しません。** 番号が同じまま文面が変わったら、前後の文面を報告に載せ、
  人とレビューが読みます（不合格にはしません）。要件のファイルを変えるには、変更記録の `requirements` にその要件が要ります。
- **Claude Code が worktree で作業するとき（デスクトップアプリの既定）。** hook に渡るプロジェクトのフォルダは、元のフォルダの
  ままです。hook は、編集されるファイル（または作業中のフォルダ）から上にたどって、検査ツールと台帳を持つフォルダを探し、
  そのプロジェクトを検査します（元のフォルダの内側だけ）。ただし、**実行される hook の本体は、元のフォルダにある版**です。
  hook を直したら、元のフォルダ（`main`）に取り込むまで、新しい hook は働きません。この版より前の hook は、worktree の中の
  編集を「プロジェクトの外」とみなし、編集時の停止・確認のダイアログ・作業を終えるときの検査が、どれも働いていませんでした
  （コミット前の検査と品質ゲートは、worktree の中で動くので働いていました）。
- **シェルから書き込まれた承認は、既定では確認が出ません。** `.claude/settings.json` の PreToolUse の matcher に `Bash` を
  足すと、`approved_by` に触れるコマンドに確認が出ますが、コマンドの文字列を見るだけなので、別のスクリプトを介した書き込みは
  捕まえられません。どの経路で書かれた承認も `regress` の報告と、作業を終えるときの hook の出力に載るので、取り込む前に読みます。
- **確認のダイアログは Claude Code の機能に頼っています。** 権限の確認をすべて省くモードで出るかどうかは確かめていません。
  ほかのエージェントでは出ません（承認の記録と、`regress` の報告で補います）。
- **変更前の状態は、毎回、一時フォルダに取り出して読みます。** 大きなリポジトリでは、作業を終えるときの hook と
  コミット前の検査が、その分だけ遅くなります。約16万行・2,400ファイルの合成データでは、`regress` が約0.4秒、
  `guard --base main` が約0.6秒でした。それより大きな規模では測っていません。
- **CI の設定が正しいかは、文面からしか見ていません。** `doctor` は、行の先頭から `python` で `guard` と `verify.py` を
  呼んでいるかを見ますが、`if false; then … fi` の中にあるような形までは見抜けません。「導入したあとの受け入れ確認」で、実際に止まることを確かめます。
- **GitHub の上では、まだ動かしていません。** CI の例（取り込み先の検査ツールで番人を動かす手順）は、手元で同じコマンドを
  実行して確かめただけです。ブランチの保護とコードオーナーの設定も、実際のリポジトリでは試していません。
- **品質基盤の承認は、名前の記録です。** 承認した人の名前は、書こうと思えば誰でも書けます。検査は「記録のない変更」を止め、
  誰が認めたことになっているかを差分に残しますが、本人が認めたことまでは確かめられません。確実に止めるのは、
  ブランチの保護とコードオーナーのレビューです。
- **品質基盤として見るのは、プロジェクトのルートの下だけ**です。リポジトリの一部に入れた場合（モノレポ）、
  リポジトリのルートにある `.github/workflows/` はプロジェクトの外なので、番人の対象になりません。コードオーナーで守ります。
- **テストファイルそのものは、品質基盤に入れていません**（変更のたびに書き換えるものなので）。テストの削除や期待値の緩和は、
  受け入れ条件にテストがなくなれば `REQ-AC-UNTESTED` で落ちますが、ファイルが残っていれば機械では分かりません。レビューで見ます。
- **変更記録は、空欄でないことしか見ません。** 影響分析の質は見ません。
- **テストのレベルとゲートの対応は、名前の一致（または `levels` の宣言）で見ます。** ゲートのコマンドが、そのレベルのテストファイルを本当にすべて実行しているかまでは見ません。
- **編集の時点で止められるのは Edit / Write による編集だけ**です。シェルのコマンドでファイルを書き換えれば、その場では止まりません。作業を終えるときの hook が、範囲の外の未コミットの変更として指摘し（git の管理下にある場合）、コミット前と CI の `guard` が同じ規則で止めます。
- **Windows では動作を確かめていません。** 日本語環境のコンソール（cp932）で表示できない文字があっても異常終了しないことは、文字コードを切り替えたテストで確かめていますが、Windows の実機では試していません。
- **大きなリポジトリでの速さ。** 180万行・30コンポーネント・要件300件の合成データで、`check` は約5秒、編集のたびに走る hook は約0.3秒でした。`check` は作業の開始時と終了時の hook でも走ります。
- **Claude Code 以外のエージェントでは hook が働きません。** `AGENTS.md`・コミット前の検査・CI の3つで守ります。
- **実際の開発での運用は、まだ試していません。** 検査ツールは自動テストとサンプルで確かめていますが、skill・サブエージェント・hook を実際のセッションで通しで使った確認は、これからです。

## 参考にした考え方

特定の道具の書式には依存せず、考え方だけを取り入れています。

- 仕様駆動開発（Spec Kit、Kiro、OpenSpec など）: 要件 → 設計 → 実装の工程と、工程の間の関門。変更を1件ずつの記録として残すこと。受け入れ条件を WHEN / THEN の形で書くこと。
- 要件トレーサビリティの道具（OpenFastTrace、Doorstop、StrictDoc など）: IDによる対応づけ。要件ごとに「どのレベルの検証が要るか」を宣言し、足りないものを機械で検出すること。
- テスト駆動の規律（Superpowers、TDD Guard など）: テストを先に書くこと。完了を主張する前に、いま実行した結果を根拠にすること。hook で止めること。
- 進化的アーキテクチャの適応度関数、アーキテクチャテスト（ArchUnit、import-linter、dependency-cruiser など）: 設計の約束を、実行できる検査として持つこと。
- 設計判断の記録（ADR / MADR）、アーキテクチャ文書の構成（arc42、C4）。
